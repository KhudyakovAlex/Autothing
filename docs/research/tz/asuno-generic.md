# Разбор ТЗ: типовое ТЗ на АСУНО (эквивалент нашей новой платформы)

> Источник: `PRD_examples/asuno-tz.md`. Разбор от 2026-10-10.
> Короткое типовое ТЗ. Ориентир в ТЗ — наша новая платформа (первый носитель онтологии autothing); ТЗ написано заказчиком под неё. Нового для модели немного, но фиксирует минимальный набор, который заказчик по освещению считает обязательным.

## Минимальный обязательный набор (по этому ТЗ)

- Сбор состояния оборудования, учёт электроэнергии **по каждому шкафу**.
- Аварии: дверь шкафа, изменение состояния пункта включения, **несанкционированное подключение к сети**, авария канала связи.
- Три режима: автоматический (расписание светового дня или фотореле), ручной дистанционный (АРМ), ручной аппаратный (по месту).
- Расчётные задачи, включая **расчёт наработки**.
- Журнал событий, архив параметров, сменные и месячные отчёты.
- Не менее **3 диспетчерских пунктов** одновременно.
- Сроки восстановления: ПО — 2 суток, оборудование — 4 суток.

## Что добавляет к модели

- **Наработка** (часы горения, моточасы) — накопительная расчётная точка данных актива, считается из интервалов состояния «включён». Ещё один аргумент за состояние как интервал.
- **Несанкционированное подключение** — событие, выводимое из расхождения ожидаемой и фактической нагрузки на линии. Требует: у линии есть ожидаемая нагрузка (сумма мощностей подключённых светильников по модели) и фактическая (по счётчику). → Производная точка данных + правило.
- **Несколько диспетчерских пунктов** — несколько субъектов-операторов с одновременным доступом к одним объектам; у нас покрыто ролью 2 и связями «эксплуатирует».
- **Сроки восстановления** — атрибут договора обслуживания, а не актива. Связь «обслуживает по договору» несёт SLA.
- **Критерий эквивалентности** продукту-ориентиру — для нас это чеклист функционального минимума по вертикали «улицы».
