# Разбор ТЗ: диспетчеризация инженерных систем складского комплекса, Заказчик 3

> Источник: `PRD_examples/customer3-tz.docx`. Разбор от 2026-10-10.
> Первый документ по вертикали **BMS**. Проверяет, что модель, построенная на освещении, не ломается на здании.

## Контекст

- Объект: склад + АБК (административно-бытовой корпус). Есть проектная документация по АСД.
- Работы — только ПНР (15 рабочих дней). Система должна жить ≥5 лет, доступность 99,9 %, отклик ≤2 с.
- Подсистемы: вентиляция АБК, теплоснабжение (ИТП), воздушное отопление склада (Hoval), отопление АБК, водоснабжение, электроснабжение (ТП, два ввода), холодоснабжение. Противопожарные — вне управления, но в KPI (АУПТ, АПС, СОУЭ).

## Что ТЗ говорит о модели

### Структура

- **Здание → подсистема → установка → параметр.** Подсистема здесь — главная ось навигации (как в нашей действующей BMS). Иерархия мест: комплекс → склад / АБК → помещение (компрессорная, ИТП, лестничная клетка).
- Установка (вентустановка, ИТП, воздушный отопитель Hoval Р6, циркуляционный насос ГВС) — актив с составом: насосы, фильтры, датчики.
- **ТП с вводами 1 и 2 и счётчиками 1.1 / 1.2 / 2.1 / 2.2**: напряжение, частота, качество по вводу — **производные от показаний нескольких счётчиков**. Ввод — сущность между ТП и щитами; точка данных «напряжение ввода» вычисляется из точек данных приборов. → Производные (виртуальные) точки данных — в ядро.
- Электроснабжение: та же ТП, что и в освещении, — одна ось питания для разных вертикалей.

### Точки данных и состояния

- У точки данных есть **факт и уставка** (температура в канале — измеренная и установленная). Уставка — тоже точка данных, но управляемая, со своей историей.
- **История изменения уставок с указанием, кто менял: вручную по месту или дистанционно.** → Событие «изменение уставки» с субъектом и каналом воздействия (местный / дистанционный / автоматический).
- Три режима управления (как и в АСУНО): автоматический, ручной дистанционный, ручной местный. → Режим — состояние актива.
- Режимы объекта: **зима / лето**, **рабочий / дежурный (08:01–20:00 / 20:01–08:00)**. Режим привязан к зданию или подсистеме, влияет на нормы и алгоритмы. → Режим как состояние Места/Подсистемы с расписанием.
- Четырёхцветная индикация: норма / предупреждение / авария / отключено. Плюс статус «не готов» для KPI. → Качество значения + уровень тревоги — отдельные измерения одной точки данных.
- Состояние фильтра: замена по аварийному сигналу или по регламенту — ТЗ само ставит вопрос. → Событие ТО бывает реактивным и плановым; оба ссылаются на один актив.

### Время и агрегаты

- **Коэффициент готовности** = (минуты периода − минуты в статусе «не готов») / минуты периода. Требует хранить состояние «не готов» как **интервалы времени**, а не как мгновенные события. Подтверждает 4D: состояние — временная часть.
- Сравнение с **АПГ** (аналогичный период прошлого года), корреляция с наружной температурой, удельный расход на м² / м³. → Площадь и отапливаемый объём — атрибуты Места; нормативы — эталонные данные с датой.
- Отчёт по расходу: показания на 0:00 первого числа двух месяцев → потребление. Точка данных накопительная; срез на момент T.
- **Ежедневный отчёт в 8:00 для службы эксплуатации**: критические (немедленно) и предупреждения (в течение смены), по системам, с оборудованием. → Это автоматическая генерация **нарядов** из событий. Подтверждает наряд как сущность с приоритетом и сроком реакции.

### Алгоритм утечки — правило над моделью

Детекторы: возможная утечка (ночью расход > нормы дольше 30 мин, стабильный), критическая (расход > порога в любое время), рост базового расхода (текущие сутки vs среднее за 7–14 дней в том же режиме). Выход — сигнал + расчётный объём потерь + **действие для бригады**.

Для модели: правило ссылается на точку данных, режим объекта, исторические агрегаты и производит событие с рекомендованным нарядом. Само правило — вне ядра онтологии (логика), но все его входы и выходы — сущности ядра.

### Роли

- **Оператор ЦДП / диспетчер** — наблюдает, меняет уставки дистанционно.
- **Служба эксплуатации / бригада** — получает ежедневный отчёт-задание, реагирует. Роли 3–4.
- **Заказчик** согласует эскизы мнемосхем, формы отчётов, материалы. Роль 7.
- **Подрядчик ПНР** — конфигурирует, сдаёт по приёмке. Роль 6.
- Персонал с местным управлением — тот, кто крутит уставку по месту. Это Пользователь (роль 1) или Исполнитель (4)? Для модели важно только, что изменение пришло «по месту».

## Проверка «здание и регион»

Модель, собранная на освещении, здесь работает: та же ТП, те же активы с составом, те же события, наряды, режимы, уставки. Новое — **подсистема как функциональная ось**, **производные точки данных**, **уставка как управляемая точка данных с историей**, **режимы объекта**, **состояние как интервал** для KPI. Ничего из этого не специфично для BMS — уличное освещение тоже имеет режимы (вечер / ночь), уставки (уровень диммирования) и готовность.
