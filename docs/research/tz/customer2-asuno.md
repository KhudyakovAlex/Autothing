# Разбор PRD: внедрение нашего АПК, Заказчик 2 (муниципальное предприятие, наружное освещение)

> Источник: `PRD_examples/customer2-prd.pdf` (ред. 27.02.2026). Разбор от 2026-10-10.
> **Это наш текущий продукт**; PRD составлен нами после общения с заказчиком. Ценность документа: в нём явно зафиксирована **наша текущая модель объектов**, от которой autothing отталкивается. Сравнение ниже — это «что autothing добавляет к текущей модели», а не критика чужого.

## Контекст

- Заказчик — муниципальное предприятие, содержащее сети наружного освещения города. Исполнитель — мы, продукт — наш АПК.
- Оборудование в ШУНО: наш контроллер, Modbus-модуль, PLC-шлюз, релейный модуль. Сервер ↔ контроллеры по REST API с токенами.
- Основная операционная среда — **цифровая тень** с 3D-картой территории; оборудование геопривязано с высотой.

## Текущая модель объектов

| Понятие в PRD | Определение в документе | Соответствие в autothing |
|---|---|---|
| Устройство | инженерное устройство (светильник, контроллер) | Актив |
| Соединение | средство передачи ресурса / вещества / информации (силовой кабель, оптоволокно) | Актив особого рода + связь «соединяет». У нас не выделено явно — **линия** из ТЗ Заказчика 1 сюда же |
| Несущая конструкция | сооружение для монтажа устройств или прокладки соединений (опора, эстакада) | **Ответ на наш открытый вопрос «опора — место или актив»**: опора — актив типа «несущая конструкция», на который через связь «смонтирован на» ставятся устройства и соединения |
| Оборудование | устройства + соединения + несущие конструкции | Актив (общая категория) |
| Подсистема | часть инженерной системы с функцией (освещение) | Функциональная ось группировки — ещё одна иерархия/группа над активами |
| Цифровая тень | виртуальная модель + 3D + карта + параметры для управления | Цифровой двойник в терминах AGENTS.md |

Триада **устройство / соединение / несущая конструкция** — проверена внедрениями, чистая и прикладная. Берём как первый уровень специализации Актива в ядре autothing.

## Что из текущей модели переносится в autothing

- **Произвольные справочные параметры** у любого оборудования: «Название — Тип — Значение», тип может быть «выбор из справочника»; справочники ведутся при внедрении и эксплуатации. → Схема атрибутов расширяема без изменения ядра; справочники — мастер-данные (граница из `README.md`).
- **Вывод из эксплуатации не удаляет объект**: признак + дата/время. → Фаза жизненного цикла с временной меткой; история не теряется. Совпадает с 4D-подходом.
- **История изменений по каждому экземпляру** оборудования; все действия пользователей, меняющие БД, фиксируются. → Provenance на уровне ядра.
- **События привязываются к объектам**: действия пользователей, аварии, периоды отсутствия связи, команды контроллеров, телеметрия — всё в одной базе, всё ссылается на объект цифровой тени. → Событие как категория подтверждено; **период отсутствия связи — тоже событие с интервалом**.
- **Группы устройств** (группы светильников) с расписанием и оперативным управлением. → Группа — подтверждена вторым ТЗ.
- **Карточка-мнемосхема** у каждого устройства, соединения, конструкции, шкафа — вид зависит от типа. → Тип определяет представление; у нас Тип — категория.
- **Иерархия ролей**: роли включают другие роли; действия как объекты прав; активность пользователей (сессии, действия) отслеживается. → Модель прав — отдельная, но «действие над объектом» — общий словарь с онтологией.
- **3D-карта актуализируется, оборудование и его геопривязка при этом не меняются** → координаты — свойство актива, а не карты; карта — подложка.
- **Расширение цифровой тени другими подсистемами без отдельного ПО** — то же, что наш принцип «общая модель для всех вертикалей».

## Что autothing добавляет к текущей модели

- **Владение и субъекты**: кто владелец, кто эксплуатирует, по какому договору — сейчас не моделируется, в autothing — ядро.
- **Временная валидность связей**: сейчас история есть у атрибутов, но не у связей «смонтирован на», «питается от». В autothing — у всех связей.
- **Федерация узлов**: сейчас — один сервер у заказчика; autothing — edge → региональный → центральный.
- **Внешние идентификаторы и маппинги** к стандартам (AAS, NGSI-LD, Brick).
- **Уровни выше территории одного предприятия**: регион, страна.
- **Наряд / заявка** как сущность; сейчас — события и отчёты, но не рабочий процесс.
