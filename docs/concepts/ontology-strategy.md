# Стратегия онтологии: своё ядро, маппинги на границах

> Решение от 2026-10-10. Уточняет п. 4.2 и 4.3 AGENTS.md.

## Позиция

Внешние онтологии и схемы (Brick, Haystack, SAREF, AAS, NGSI-LD) — **не догма**. Ядро autothing строится на собственной онтологии; к внешним стандартам делаются маппинги на границах системы.

Это зеркало принципа из п. 4.3: протоколы — через адаптеры на периферии, не в ядре. С онтологиями то же самое.

## Почему не взять Brick как основу

Brick — хороший ориентир для зданий, но покрывает одну из трёх вертикалей и один уровень иерархии из семи:

- Заточен под здания и HVAC. Освещение улиц и трасс, шкафы, клеммы, выходы, кабельные трассы — вне его зоны: ниже «оборудования» ничего нет.
- Нет времени у связей: `ownedBy`, `feeds`, `hasLocation` — плоские свойства без валидности (см. [`4d-ontology.md`](4d-ontology.md)). Единственное время — `rec:Event` со start/end.
- Владение и жизненный цикл есть только через REC (`ownedBy / operatedBy / servicedBy`, `installationDate`, `commissioningDate`, `Lease`, `WorkOrder`) — но без истории и без договорных связей как сущностей.
- Выше здания — `Portfolio → Region → Site → Campus` из REC, но это группировка недвижимости, а не административно-территориальная иерархия с автономными узлами.

Аналогичные ограничения, каждый в своей зоне, есть у Haystack (здания, теги вместо строгой модели), SAREF (IoT-устройства, без иерархии активов), AAS (отдельный актив, без территориальной иерархии).

### Brick как пример «большого и доброго»

По `Brick.ttl` v1.5.0-rc.2 (57 тыс. строк, локальная копия в `brick/`, проверено 2026-10-11):

- **Ядро связей маленькое** — ~22 структурных отношения (hasPoint, feeds, hasPart, hasLocation, controls, hosts, meters, hasSubstance…). Это как раз хорошо.
- **Словарь листьев огромный и добрый** — 1470 классов brick: + 270 rec:. Из них 309 `*Sensor`, 87 `*Temperature_Sensor` (`Medium_Temperature_Hot_Water_Return_Temperature_Sensor`). Комбинаторика «субстанция × величина × роль» развёрнута в классы вместо композиции. 255 пометок `owl:deprecated`. REC добавляет ~200 типов помещений и мебель (Sofa, WasteBasket).
- Сшивание словарей (REC, 223P, QUDT, BACnet, ref) заплатками: `brick:Collection` → `rec:Collection`, `connectedTo` удалён, появились `controls` / `hosts` — структурные связи меняются между минорными версиями.
- 1791 SHACL-шейп (`sh:NodeShape`) — валидация серьёзная, это злая часть.

Вывод: доброта Brick — не в ядре, а в словаре. Урок для autothing: типы оборудования и точек — **композиция** (Точка данных = величина + субстанция + роль + место), а не класс на каждую комбинацию.

Что заслуживает заимствования: SHACL-валидация; величины через QUDT; **REC** как ориентир для Субъекта (`Agent / Person / Organization`), наряда (`WorkOrder`), документа, события с интервалом (`Event`); **ASHRAE 223P** — модель `Connection` / `ConnectionPoint` / `Medium` для соединений и потоков. Брать точечно, не словарём.

### Перекос Brick в HVAC

Происхождение: академические проекты по данным BMS университетских кампусов (Berkeley, UCSD, CMU, 2016), затем ASHRAE — общество инженеров по отоплению и кондиционированию. Отсюда состав словаря 1.5:

- HVAC — ориентировочно две трети оборудования и точек: 87 датчиков температуры, десятки `*_Water_System` / `*_Air_Loop`, VAV, AHU, чиллеры, градирни.
- Электрика — заметно меньше; счётчики, инверторы, PV, EV-зарядки добавлены недавно.
- **Освещение — около 20 понятий**: `Luminaire`, `Luminaire_Driver`, `Light_Source`, `Lighting_Zone`, `Illuminance_Sensor`, `Lighting_Level_Command`, CCT-команда. Нет сцен, профилей, групп, DALI-адресации, аварийного и уличного освещения. У REC зоны освещения нет вовсе.
- Безопасность, ОПС, лифты, водоснабжение — единицы классов. Уличная инфраструктура — ноль.

Следствия для autothing:
- Маппинг к Brick реально полезен в одной зоне — ИТП, вентиляция, холодоснабжение (сценарий С6, Заказчик 3). Там словарь богатый.
- В нашей сильной зоне — освещении — учиться у Brick нечему. Светотехническая часть нашей онтологии может стать вкладом в REC lighting working group, который в 1.5 только начал выравнивать классы освещения.

## Краткое обоснование (для руководства)

Brick — хороший отраслевой словарь для зданий; совместимость с ним держим через маппинг. Как основа платформы не подходит:

1. **Таксономия, а не онтология.** Ядро — ~20 связей, словарь — 1460 классов, класс на каждую комбинацию. Растёт комбинаторно, ломается между минорными версиями (255 deprecated, базовые связи удаляются и переименовываются), правил не даёт. Нужна модель, где типы собираются из признаков, а не перечисляются.
2. **Нет нашего нижнего уровня.** Заканчивается на «оборудовании»: шкаф → контроллер → выход → линия → клемма отсутствуют. Это основа и BMS, и АСУНО.
3. **Нет нашего верхнего уровня.** «Регион» — группировка портфеля недвижимости. Территориальной иерархии с ответственными, автономными узлами и федерацией нет. Улицы и трассы как предметная область отсутствуют.
4. **Нет времени у связей.** Владелец, эксплуатант, подключение — плоские свойства. «Кто отвечал за объект на дату аварии» не выражается. Для энергосервиса, гарантий и передачи между подрядчиками — критично.
5. **Чужая скорость и приоритеты.** Развивается под HVAC американских офисов и ASHRAE; каждое наше требование — заявка в чужой консорциум с горизонтом в годы.

Делаем собственное компактное ядро (~8 категорий), проверенное на реальных ТЗ и восьми годах нашей цифровой тени. Из Brick, REC, 223P, QUDT берём точечно; маппинг держим для обмена. Это дешевле, чем подстраивать продукт под чужую модель и потом годами жить с её ограничениями.

## Что это значит на практике

1. **Ядро** — онтология autothing: иерархия активов (раздел 2 AGENTS.md), владение, жизненный цикл, временная валидность, подключения. Определяется нами, версионируется нами.
2. **Маппинги** — для каждого внешнего стандарта отдельный модуль «наше понятие ↔ их понятие». Используется при импорте/экспорте и интеграции с чужими системами. Неполнота маппинга допустима: не всё наше есть у них, не всё их нужно нам.
3. **Заимствование** — конкретные удачные решения внешних онтологий (например, типология оборудования Brick, подмодели AAS для паспортов устройств) можно брать внутрь ядра осознанно, по одному, а не целым стандартом.
4. **Top-level** — фундаментальные понятия (вещь, событие, часть–целое, время) не изобретаем: опираемся на устоявшиеся, но тоже без обязательства тащить чью-то top-level онтологию целиком.

## Критерий

Любое решение по онтологии проверяется вопросом из п. 6 AGENTS.md: работает ли это для одного здания **и** для региона. Brick этот тест не проходит сам по себе — поэтому он маппинг, а не ядро.
