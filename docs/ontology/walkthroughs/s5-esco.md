# Прогон С5 «Энергосервисная замена сети освещения» через ядро

> Статус: **черновик**. Изменено: 2026-10-10.
> Сценарий — [`../scenarios.md#с5`](../scenarios.md). Категории — [`../core-categories.md`](../core-categories.md).
> Цель прогона: провести каждый шаг сценария через 8 категорий, зафиксировать, где модель держит, где течёт, и какие открытые вопросы это закрывает. Решения, принятые здесь, перенесены в `core-categories.md`.

## Условные обозначения

`А` Актив · `М` Место · `С` Субъект · `→` Связь (с интервалом) · `Т` Точка данных · `Е` Событие · `Тип` · `ID` Идентификатор.
Каждая граница интервала связи ссылается на Событие-источник (решение Р2 ниже).

## Действующие лица

- `С` Заказчик (администрация города) — владелец сети после акта.
- `С` ЭСКО — обследует, монтирует, передаёт, гарантирует; до акта владеет новым оборудованием.
- `С` Сетевая компания — владеет ТП.
- `С` Обслуживающая организация — эксплуатирует по договору.
- `С` Третьи лица — владельцы камер и вышек на опорах.

## Шаги

### Ш1. Обследование

По каждой опоре: что стоит, что планируется. Часть опор пустые; на части — чужое оборудование.

| Факт сценария | Выражение в ядре |
|---|---|
| Опора | `А` несущая конструкция (решение из PRD Заказчика 2). Расположена `→ расположен в` `М` точка на карте / участок улицы |
| Существующий светильник на опоре | `А` светильник `→ смонтирован на` опора; позиция на опоре — атрибут связи |
| Планируемый светильник (тип, мощность) | `А` в фазе жизненного цикла **проект**, `Тип` = целевая модель, `→ смонтирован на` опора (валидность — с даты схемы), `→ заменяет` существующий светильник |
| Опора без светильника | запрос: опоры без действующей связи `смонтирован на` с активом типа «светильник». Новых понятий не нужно |
| Чужая камера на опоре | `А` камера `→ смонтирован на` опора; `С` третье лицо `→ владеет` камера. Если владелец неизвестен — связи `владеет` просто нет; запрос «чьё» возвращает «не установлено» |

**Держит.** Ничего добавлять не пришлось.

### Ш2. Согласование схемы

`Е` «согласование схемы»: участники — ЭСКО, Заказчик; вложение — файл схемы. Все проектные активы Ш1 получают фазу «проект» с валидностью от этого события. Светильники, которые будут заменены, не меняют состояния — пометка «планируется к замене» **производная**: существует проектный актив со связью `заменяет` на них.

**Держит.** Схема как документ — вложение События, не сущность (решение Р3).

### Ш3. Монтаж

Фактически смонтированная модель иногда отличается от схемы.

`Е` «монтаж» (дата, исполнитель-бригада `С`, фото во вложении) порождает атомарно:
- конец `старый светильник → смонтирован на опора`;
- начало `новый светильник (А, фаза «смонтирован») → смонтирован на опора`;
- начало `новый → реализует → проектный актив`; проектный актив получает фазу «реализован» и дальше не меняется;
- начало `новый → питается от → линия` (наследуется от опоры по правилу, но хранится явно — иначе срез «на момент T» потребует вывода).

Расхождение факт/проект — сравнение `Тип` фактического и проектного актива через связь `реализует`. «Что по проекту ещё не смонтировано» — проектные активы без связи `реализует`.

**Держит, с оговоркой.** Удвоение записей (проектный + фактический) на 2889 объектов — цена честного ответа на вопросы монтажа 1, 3, 4 и проектировщика 5. В массовом случае «факт = проект» фактический актив создаётся копированием проектного — это UX, не модель.

### Ш4. Передача демонтированного, склад

- Старый светильник: фаза **выведен**; `→ находится в` `М` склад. Владелец не меняется — он и был у Заказчика.
- `Е` «передача по акту»: участники — ЭСКО (передал), Заказчик (принял), список активов; вложение — акт.

**Держит.** Склад — Место, не фаза жизненного цикла (решение Р4). Актив без места в сети питания продолжает существовать с историей — это просто актив, у которого нет действующей связи `питается от`.

### Ш5. ПНР, замер освещённости, акт приёма-передачи

| Факт | Выражение |
|---|---|
| Замер люксметром по участку | `Т` «освещённость» принадлежит `М` участок; значение с источником `Е` «замер» (ручное измерение, протокол во вложении). Решение Р5: Точка данных у Места допустима |
| Нормативный класс участка | атрибут `Типа` места («участок улицы класса Б1») или связь `М → нормируется → норматив`; подтверждение замером — сравнение `Т` с нормой. В ядро новых понятий не нужно |
| Акт приёма-передачи оборудования | `Е` протяжённостью в момент; порождает: начало `Заказчик → владеет → новые активы` (конец `ЭСКО → владеет`); начало `ЭСКО → гарантирует → активы`, valid_to = дата + 7 лет; начало `Обслуживающая организация → эксплуатирует → активы`; фаза активов → **в эксплуатации** |
| Договор (энергосервисный, обслуживания) | `Е` **протяжённое** (решение Р6): участники — стороны, интервал — срок действия; связи `гарантирует`, `эксплуатирует`, `обслуживает` ссылаются на него как на основание |

**Держит.** Гарантия отсчитывается от события, а не хранится атрибутом — вопрос эксплуатации 8 закрыт.

### Ш6. Инвентарный номер №ТП/№Опоры/№Светильника

`ID` с системой-источником «инвентарная нумерация Заказчика», правило вывода — из цепочки `питается от`, валидность — пока цепочка не изменилась. Глобальный ID autothing — отдельный `ID` без валидности-конца.

**Держит.** Подтверждает Идентификатор как сущность с источником и валидностью; аргумент против слияния в атрибут.

### Ш7. Экономия к базовому году

- Потребление ШУНО — `Т` принадлежит ШУНО (не счётчику: при замене счётчика ряд не рвётся, см. С2). Счётчик `→ измеряет →` эту точку.
- Базовое потребление — `Т` «базовое потребление» у ШУНО, значения по месяцам, источник — `Е` «фиксация базы» (согласована сторонами, вложение — расчёт). Не отдельная сущность.
- Экономия — производная `Т` (разность), качество наследуется.
- Экономия по группе ШУНО — суммирование по **Группе**. Здесь модель течёт, см. ниже.

### Ш8. Перенос светильника на соседнюю опору

`Е` «перенос»: конец `смонтирован на опора A`, начало `смонтирован на опора B`; если опоры на разных линиях — то же с `питается от`. Старый `ID` инвентарный закрывается, создаётся новый. Актив тот же, история — непрерывна.

**Держит.** Это ровно 4D-случай из [`../../concepts/4d-ontology.md`](../../concepts/4d-ontology.md).

## Три иерархии над одними активами

- **Питание**: ТП → ШУНО → линия → опора → светильник — цепочка `питается от` между активами. ТП `← владеет` Сетевая компания, ШУНО и ниже `← владеет` Заказчик: граница балансовой принадлежности — производная от смены владельца вдоль оси.
- **Территория**: активы `→ расположен в` `М` (точка / улица / эксплуатационный район / город).
- **Группы**: см. «Где течёт».

## Решения, принятые по итогам прогона

- **Р1. Проектное vs фактическое — два экземпляра Актива.** Проектный живёт в фазе «проект» → «реализован» и никогда не становится физическим; фактический ссылается на него связью `реализует`. Основание: разные критерии идентичности (спецификация позиции vs вещь с серийным номером), факт может расходиться, одна позиция может быть реализована нулём или двумя активами.
- **Р2. Событие порождает изменения связей.** Каждая граница интервала связи ссылается на Событие-источник. «Кто и когда утвердил» хранится один раз — у События. Импорт, автоматическое обнаружение — тоже События (системный субъект).
- **Р3. Документ — не категория ядра.** В С5 всё документальное (схема, фото, акт, протокол) — свидетельство События: вложение с файлом, хэшем, кто приложил. Паспорт, сертификат — мастер-данные Типа. Пересмотреть при вопросах регулятора (роль 15).
- **Р4. Фазы жизненного цикла Актива в ядре:** проект → смонтирован → в эксплуатации → выведен → утилизирован; плюс «реализован» — терминальная фаза проектного актива. Склад — Место, не фаза. Фаза — состояние с интервалом.
- **Р5. Точка данных может принадлежать Месту напрямую** (освещённость участка, температура помещения). Виртуальный актив «помещение как объект контроля» не вводим.
- **Р6. Договор — протяжённое Событие**, не категория: стороны — участники, срок — интервал. Связи ответственности ссылаются на него как на основание. Проверить на С3 (передача между подрядчиками).

## Где течёт

- **Группа.** Экономия по группе ШУНО и команды/расписания на группу требуют сущности-адресата связи `входит в группу`. Варианты из `core-categories.md` (связь / Место-зона / категория) С5 не разводит: здесь группа только агрегирует. Решать на сценарии с командами на группу (ТЗ Заказчика 1, расписания).
- **Геометрия.** Опора теперь Актив — где координаты? У Места «точка», в котором опора расположена, или у самого актива? Модуль управления светильником даёт свой GPS — второй источник. Предварительно: геометрия — свойство Места; GPS модуля — `Т` «позиция» актива, из которой Место может уточняться. Закрепить в `hierarchy.md`.
- **Унаследованные связи.** `питается от` у светильника выводится из опоры, но хранится явно (Ш3). Правило «что выводится, что хранится» нужно в `hierarchy.md`, иначе срез на момент T будет то считаться, то читаться.
- **Противоречие с С1.** В С1 написано «опора — место». После решения из PRD Заказчика 2 и этого прогона — опора актив. С1 нужно поправить при его прогоне.
