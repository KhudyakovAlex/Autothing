# Хранение модели

> Статус: черновик. Обновлено: 2026-10-11. Решение по СУБД для хранения онтологической модели (объекты, связи, субъекты, время, гео, телеметрия).

## Решение

**PostgreSQL + PostGIS + TimescaleDB.** Одна СУБД, одна схема — от шкафа до региона. Графовая СУБД (Neo4j и аналоги) как источник истины не используется.

## Почему Postgres, а не Neo4j

- **Граф неглубокий.** Иерархия — ~7 уровней (страна → … → клемма), цепочки «питает» — десятки звеньев. Рекурсивный CTE справляется; преимущества графовой СУБД на глубоких обходах здесь не проявляются.
- **Время у связей.** Range-типы (`tstzrange`) и exclusion constraints: «у объекта не может быть двух владельцев одновременно» проверяет сама БД. В Neo4j темпоральность — свойства на рёбрах без ограничений целостности. Подход — [`../concepts/4d-ontology.md`](../concepts/4d-ontology.md).
- **Гео.** PostGIS: координаты объектов, треки бригад, «что в радиусе N м», привязка к линейным объектам (трассы, трубопроводы).
- **Телеметрия.** TimescaleDB в той же базе: показания точек данных, события, треки. Neo4j для временных рядов не предназначен — потребовалась бы вторая СУБД.
- **Edge и федерация.** Postgres работает на слабом железе в шкафу, реплицируется, работает автономно при потере связи. Кластер Neo4j — Enterprise-лицензия.
- **Команда и эксплуатация.** Реляционка уже в продуктах, инструменты, бэкапы и мониторинг есть.
- **Маппинги** к Brick / NGSI-LD / AAS — экспорт на границе, не требуют графового хранилища внутри.

## Когда графовая СУБД всё же понадобится

Глубокие обходы произвольной структуры («всё, на что повлияет отключение фидера через 15 звеньев»), визуальное исследование графа, Cypher для аналитиков. В этом случае — **производная read-модель**, наполняемая из Postgres, не источник истины. Альтернатива — Apache AGE (Cypher поверх Postgres).

## Принцип схемы

Тип оборудования — **данные, а не таблица.** Таблицы соответствуют категориям ядра онтологии (`core-categories.md`), а не видам оборудования.

| Таблица | Что хранит |
|---|---|
| `object` | Любой объект от региона до клеммы; `type` → справочник типов |
| `link` | Все связи одной таблицей: `from, to, kind, valid tstzrange` |
| `subject` | Организации, подразделения, бригады, сотрудники |
| `point` | Точки данных (величина + субстанция + роль + место) |
| `event` | События с интервалом |
| `type` | Справочник типов и схемы их атрибутов |

Типоспецифичные атрибуты — JSONB по схеме типа из онтологии. Общие (имя, статус, геометрия) — колонки. Геометрия — PostGIS `geometry`/`geography`. Телеметрия и треки — гипертаблицы Timescale.

Следствия:
- новый вид оборудования — запись в `type` и схема атрибутов, не миграция;
- «как было на дату X» — фильтр по `valid`, без отдельных history-таблиц;
- нет удаления — закрытие интервала.

## Источник истины

Онтология — `../ontology/schema/core.yaml` (LinkML). SQL-схема, JSON-схемы типов и валидаторы генерируются из неё. БД — производный артефакт.

## Открытые вопросы

- Bitemporal (время события и время записи) — на всех связях или только на владении/ответственности?
- Границы EAV vs JSONB для атрибутов с историей.
- Стратегия синхронизации edge ↔ регион ↔ центр: логическая репликация или событийная.
