# autothing — automate everything

> Этот файл — контекст проекта для людей и AI-агентов. Читать перед любой работой в репозитории.

## 1. Название и смысл

- **autothing** — сокращение от *automate everything* («автоматизировать всё»).
- Дополнительные трактовки, которые можно обыгрывать: *auto(every)thing*, *automate things*, *automate the thing*.
- Написание: `autothing` — для пакетов, CLI, репозиториев, URL; `AutoThing` — в заголовках, именах классов/неймспейсов.
- Слоган: **autothing — automate everything**. Расшифровку всегда писать явно (в README, описании пакета, презентациях): сама по себе она не угадывается.
- Для госзаказчиков и официальных документов допустимо иметь более формальное название платформы/концепции; `autothing` остаётся брендом ядра/движка.

## 1a. Откуда мы

- За проектом стоит команда с многолетним опытом разработки систем управления освещением и BMS (сотни внедрённых объектов). С 2018 развиваем концепцию **цифровой тени**: единая 3D-модель объекта как среда управления всеми инженерными системами. В портфеле — контроллеры, действующая BMS (почти все внедрения — здания), **новая платформа (первый носитель онтологии autothing; вертикали — улицы и трассы)** и BIM-инструмент.
- **autothing — следующий шаг, а не старт с нуля**: модель, проверенная внедрениями действующей BMS, расширяется тем, чего в ней нет для масштаба региона — субъекты и владение, время у связей, федерация узлов, открытые маппинги. Онтология одна на оба продукта: новая платформа строится на ней сразу, действующая BMS — расширяется до неё.
- Подробно — [`docs/research/background.md`](docs/research/background.md). Текущая модель объектов действующей BMS — [`docs/research/tz/customer2-asuno.md`](docs/research/tz/customer2-asuno.md).
- Для агентов: не предлагать «с нуля» то, что уже есть в действующих продуктах; сначала проверять, как это решено там.

## 2. Видение (максимальный замах)

Автоматизировать всё в масштабе страны:

- оборудование на территориях и дорогах;
- цифровые двойники городов, предприятий, терминалов;
- вплоть до последнего датчика, включая внутреннее устройство шкафов управления и силовых шкафов (клеммы, автоматы, контроллеры, кабельные трассы).

Единая иерархия активов: **страна → регион → город/объект → здание/участок → шкаф → устройство → клемма/датчик/канал**.

Аналоги и ориентиры: UK National Digital Twin, Virtual Singapore, Asset Administration Shell (Industrie 4.0). Замах соответствует мировому тренду, а не является изолированной идеей. Разбор — в [`docs/research/reference-projects.md`](docs/research/reference-projects.md).

### Зачем такой масштаб

- **Масштаб — проектное ограничение, а не маркетинг.** Модель, спроектированная под одно здание, при выходе на город превращается в зоопарк. Если с первого дня держать «страна → … → клемма», иерархия, идентификация и владение проектируются правильно сразу.
- **Вертикали уже регионального масштаба.** Уличное освещение и трассы — это города и тысячи километров; заказчик — государство и муниципалитеты. Продукт без масштабирования по территории туда не продаётся.
- **Ценность — в данных, и она растёт нелинейно.** Включить реле умеет любой контроллер. «Чей шкаф, где, с чем связан, как менялся» — почти никто. Мастер-данные одного здания стоят мало, региона — очень много.
- **Защита от конкуренции.** Ещё одна BMS/SCADA не нужна. Платформа с единой онтологией, растущая с каждым внедрением, — другая категория.

## 3. Текущий фокус (дорожная карта узкая)

Актуально сейчас:

1. **BMS** — диспетчеризация и автоматизация зданий.
2. **Уличное освещение** — города.
3. **Освещение федеральных трасс**.

Принцип: **концепция — на максимум, продукт — узкий.** Продаются и внедряются конкретные вертикали (BMS, освещение). Платформа растёт за счёт каждого внедрённого вертикального кейса, а не за счёт попытки покрыть всё сразу.

Первая версия — честный BMS + освещение **на общей модели объектов**, а не два отдельных продукта.

## 4. Архитектурные принципы

### 4.1. Единый стек для всех вертикалей

`датчик/исполнительный механизм → контроллер → шлюз → платформа → цифровой двойник → аналитика / управление`

BMS здания, уличный светильник и шкаф на трассе отличаются только протоколом внизу и моделью объекта вверху. Всё между ними — общее.

### 4.2. Единая модель объектов с первого дня

- Общая онтология активов, идентификация, иерархия, владение, жизненный цикл.
- Версионирование цифровых двойников.
- Проектируется до первой вертикали, иначе получится зоопарк, который потом дорого сшивать.
- Рабочая область по онтологии — [`docs/ontology/README.md`](docs/ontology/README.md): порядок шагов, статусы, правила для агентов.

### 4.3. Открытые стандарты, никакого вендор-лока

Опираться на:

- **Здания / BMS:** BACnet, Modbus, KNX, DALI / D4i.
- **Промышленность:** OPC UA, Modbus, IEC 61850 (энергетика).
- **IoT / транспорт данных:** MQTT (Sparkplug B), LwM2M, LoRaWAN, NB-IoT.
- **Семантика / двойники:** NGSI-LD (FIWARE), Asset Administration Shell, Brick Schema / Haystack для зданий.

Проприетарные протоколы — только через адаптеры, не в ядро.

Внешние онтологии (Brick, Haystack, SAREF, AAS, NGSI-LD) — ориентиры, а не догма. Ядро — собственная онтология autothing; к внешним стандартам — маппинги на границах. Обоснование — в [`docs/concepts/ontology-strategy.md`](docs/concepts/ontology-strategy.md). Локальная копия Brick 1.5 — [`brick/`](brick/README.md) (v1.5.0-rc.2); схему брать оттуда, не из сети.

### 4.4. Данные важнее автоматизации

Главная сложность проекта — не включить/выключить реле, а ответить на вопросы: кто владелец объекта, как он идентифицируется, как связан с другими, как изменялся во времени. Модель данных и мастер-данные активов — приоритет. Подход к изменениям во времени — в [`docs/concepts/4d-ontology.md`](docs/concepts/4d-ontology.md).

### 4.5. Масштабируемость по территории

Архитектура должна одинаково работать для одного здания и для региона: иерархическое развёртывание (edge → региональный узел → центральный), автономная работа edge при потере связи, федерация данных.

## 5. Риски и как с ними работать

| Риск | Ответ |
|---|---|
| «Автоматизировать всё» нельзя продать и построить | Продаём вертикали, строим платформу под ними |
| Зоопарк моделей данных | Единая онтология до первой вертикали |
| Вендор-лок | Открытые стандарты, адаптеры на периферии |
| Завышенные ожидания от названия/слогана | Чёткая дорожная карта, честное описание текущих возможностей |
| Легковесность имени для госсектора | Отдельное формальное название концепции, `autothing` — бренд ядра |

## 6. Указания для AI-агентов

- Любое проектное решение проверять вопросом: «это работает для одного здания **и** для региона?»
- Не добавлять в ядро специфичную для вертикали логику — выносить в модули/адаптеры.
- Не вводить проприетарные форматы там, где есть открытый стандарт.
- При работе с моделью объектов — соблюдать иерархию из раздела 2 и не создавать параллельных иерархий.
- Расшифровку названия (*automate everything*) указывать в пользовательской документации и описаниях пакетов.
- Термины (онтология, таксономия, 4D, тень/двойник, наряд) употреблять в смысле [`docs/concepts/glossary.md`](docs/concepts/glossary.md).
- Отвечать кратко; код не выводить без запроса; при необходимости уточнения — задавать вопросы с пронумерованными вариантами ответов.
